# ntos: виконавча система NT у ядрі, без wineserver

Рішення користувача 2026-11-22: wineserver зникає повністю, одним оновленням,
після перевірки у VM усього, що можна перевірити. Вимоги:

- **100% його функцій.** Жодна програма і жодна частина системи не має
  помітити різниці, крім швидкості.
- **Архітектура якомога ближча до Windows:** компоненти ntoskrnl (Ob, Ke, Io,
  Cm, Ps, Se, Mm, Dbgk, Lpc, dxgkrnl) у ядрі; програма робить системний
  виклик і виконує його у своєму потоці.
- **Не зламати встановлену систему.** Іншої ОС на машині немає. Захист —
  відкат оновлення (`Host\Previous`) і перемикач `arctic.ntos=0` у рядку ядра,
  який повертає `ntexec` (wineserver іде в тому ж оновленні як запасний шлях).

Драйвери режиму ядра Windows (`.sys` у ядрі) — пізніше, окремо. Черга IRP
до windevice, яку переносимо тут, — та сама, через яку вони підуть потім.

## Що беремо звідки

- **Поведінка — з wineserver**, 1:1. Клієнти (ntdll, win32u, conhost,
  ntoskrnl.exe, драйвери дисплея) говорять його протоколом; щоб поведінка
  не змінилась, обробники переносяться майже без змін, як у win32k
  (`docs/win32k.md`, `tools/ntuser/port.py`).
- **Будова — з Windows.** Файли розкладаються за компонентами ntoskrnl, імена
  об'єктів і порядок дій беремо з документації Windows та з ReactOS у
  `D:\WORK_YT\project_arctic_nt\reactos\ntoskrnl` (форк, пре-альфа; лише як
  довідку про будову, код Wine точніший щодо поведінки, яку бачать програми).
- Ліцензії: Wine — LGPL-2.1+, ReactOS — GPL-2.0+, ядро — GPL-2.0: сумісні.

## Обсяг

wineserver: ≈60 тис. рядків, 255 обробників. USER (≈12 тис., 111 обробників)
уже в ядрі (win32k). Лишається:

| Компонент Windows | Файли wineserver | Обробників |
|---|---|---|
| Ob — об'єкти, дескриптори, простір імен | handle, object, directory, symlink | 19 |
| Ke — синхронізація | event, mutex, semaphore, timer, completion, inproc_sync | 26 |
| Io — файли, асинхронний ввід-вивід, сповіщення | fd, file, async, change | 27 |
| Io — канали, mailslot, порти | named_pipe, mailslot, serial | 6 |
| afd.sys — сокети | sock | 7 |
| Io — пристрої (IRP до windevice) | device | 11 |
| Cm — реєстр | registry | 15 |
| Ps — процеси, потоки, APC | process, thread, signal, ptrace/procfs | 45 |
| Se — токени, безпека | token, security | 15 |
| Mm — секції | mapping (+ ntimage) | 13 |
| dxgkrnl | d3dkmt | 8 |
| Dbgk — налагодження | debugger | 7 |

| механізм запитів | request, fd (головний цикл), main | — |

## Як влаштовано

```
програма → ntdll (PE) → ntdll.so: SERVER_START_REQ( … )        (без змін)
         → server_call: syscall nt_call → обробник у ядрі під замком
win32u   → те саме; запити USER — у win32k, як зараз
```

### Системні виклики

Таблиця NT стоїть перед таблицею win32k (`0x1000`), як у Windows:

| № | Виклик | Замість |
|---|---|---|
| `0x0F00` | `nt_hello` — процес або потік стає NT-потоком | під'єднання до сокета wineserver, `init_first_thread`, `init_thread` |
| `0x0F01` | `nt_call` — запит протоколу, відповідь | запис у request_fd, читання reply_fd |
| `0x0F02` | `nt_send_fd` — дескриптор файлу ядру | `sendmsg` SCM_RIGHTS |
| `0x0F03` | `nt_receive_fd` — дескриптор файлу від ядра | `recvmsg` |
| `0x0F04` | `nt_boot` — arctic-init: старт виконавчої системи | запуск `ntexec` |
| `0x0F05` | `nt_admin` — arctic-init і arctic-lxss: збереження реєстру, дерево процесів, вимкнення | дочірній процес збереження, сокет `arctic-wineserver-ntree`, `ntexec -k` |

Номери Linux (0–~470) і NT не перетинаються. Прямі системні виклики програм
повз ntdll і далі йдуть через Syscall User Dispatch, як зараз.

### Замки: як у Windows (обов'язково в цьому ж оновленні)

wineserver однопотоковий, і кожен обробник на цьому покладається. Тому
**першою** збирається версія з одним замком на всю виконавчу систему — вона
поводиться точно як wineserver і є еталоном для тестів. Але в оновлення вона
**не йде**: під навантаженням багатьох потоків вона слабша за Windows, де
замки дрібні. Перед поставкою замок розділяється так, як у Windows:

| Що | Windows | ntos |
|---|---|---|
| Таблиця дескрипторів процесу | своя для кожного процесу (ExHandleTable, push lock на запис) | своя для кожного процесу, читання дескриптора без замка (RCU), запис під замком таблиці |
| Посилання на об'єкти | лічильник, без замка | атомарний лічильник (`refcount_t`) замість `refcount++` під глобальним замком |
| Простір імен (каталоги, symlink) | замок каталогу | замок кожного каталогу об'єктів |
| Реєстр | CmpRegistryLock + замки KCB | замок дерева на структуру, замок ключа на значення |
| Файли, асинхронний ввід-вивід | об'єкт файлу, черги IRP | замок `struct fd` і його черг async |
| Процеси й потоки | замок процесу | замок процесу (список потоків, APC, стан) |
| Синхронізація | диспетчер ядра | ntsync, як зараз (уже без замка ntos) |
| USER | UserLock | win32k_lock, окремо від ntos |

Порядок замків фіксується письмово і перевіряється lockdep у VM (ядро для
тестів збирається з `CONFIG_PROVE_LOCKING`). Перемикач `arctic.ntos_lock=global`
повертає один замок — для діагностики, якщо щось розійдеться.

Що вже зроблено для цього (2026-11-23):

- **Контекст виклику на задачі.** wineserver мав один глобальний `current`
  (потік, якому служить запит) і `global_error`. У ntos це `struct ntos_ctx`
  на стеку кожного входу (`nt_call`, `nt_hello`, робота черги, вихід потоку),
  на який вказує вказівник у кожній задачі, як KTHREAD. Місце під нього дає
  LSM «ntos» без жодних хуків (`lbs_task`, `LSM_ORDER_LAST`, тобто завжди
  ввімкнене): поле в `task_struct` змінило б `sched.h` і перезібрало б усе
  ядро (півтори години), а так збирається лише ntos. `nt_current` — макрос на
  нього, код wineserver не змінювався. Виклики в різних задачах більше не
  ділять жодного «поточного».
- **Лічильники посилань атомарні** (`ObReferenceObject`), `handle_count` теж.
- **Домени і відкладене знищення.** Кожен тип об'єкта належить домену замка
  (`object_ops::domain`). Останнє посилання, відпущене без замка домену, не
  знищує об'єкт на місці: його знищує робота домену під його замком
  (`ObpDeferObjectDeletion`). Поки домен один (диспетчер), поведінка та сама.
- **Статистика замка.** Скільки разів замок був зайнятий, скільки чекали,
  які запити тримають його найдовше: `nt_admin(NT_ADMIN_LOCK_STATS)`,
  arctic-init пише підсумок у host.log кожні пів хвилини і весь список при
  вимкненні. За нею вибирається, що відділяти першим. У першому рядку — п'ять
  найдовших окремих утримань: запит за назвою або колбек воркера (`%ps`), час
  і скільки з нього на CPU (`create_file 170511/223 us` — не робота, а диск
  або витіснення). Час, коли запит сам відпустив замок (`ntos_io_begin`), не
  рахується.
- **Реєстр зберігається знімком.** Текст кущів, відформатований під замком,
  тримав усі виклики до 82 мс при кожному `RegFlushKey` і щопівхвилинному
  збереженні. Тепер під замком лише сирий знімок (два проходи: розмір, потім
  `memcpy` імен і даних, ~15 мс на 18 тис. ключів у VM), а текст робить черга
  `ntos-save` без замка (`format_branch`). `ntos.verify_registry=1` при
  вимкненні порівнює обидва шляхи байт у байт (у VM: усі три кущі однакові).

Далі: замок таблиці дескрипторів процесу; реєстр окремим доменом
(`CmpRegistryLock`), який бере замок диспетчера вкладено лише щоб будити
потоки й ставити таймери; потім домени за статистикою.

### Решта відмінностей у швидкості від Windows (теж у цьому оновленні)

- **Винятки й APC без сигналів Linux.** Зараз виняток програми — сигнал Linux,
  який `ntdll.so` перекладає в подію NT, а APC і призупинення будять потік
  `SIGUSR1`. Це в кілька разів дорожче, ніж у Windows. ntos доставляє їх сам:
  при виході з ядра в потік із чергою APC або при винятку ядро кладе контекст
  на стек потоку і передає керування диспетчеру ntdll
  (`KiUserApcDispatcher`, `KiUserExceptionDispatcher`), як Windows. Потрібен
  патч ядра на шляху повернення в режим користувача (як `task_work`).
  Еталон поведінки — поточний шлях через сигнали; тести винятків Wine
  (`ntdll:exception`) мають давати той самий результат.
- **Імена без урахування регістру на NTFS.** Пошук файлу за ім'ям у
  будь-якому регістрі — у ядрі, у словнику імен (dcache) драйвера NTFS з
  таблицею upcase тому, як робить NTFS у Windows; ntdll перестає перебирати
  каталог при промаху. Еталон — `0137` і тести `ntdll:file`, `kernel32:file`.
  Зроблено (патч ядра `0009`): на томі `nocase` dentry хешуються й
  порівнюються за таблицею upcase тому, тож ім'я в іншому регістрі знаходиться
  в dcache, а не читанням індексу каталогу (у VM «GetFileAttributes іншим
  регістром» було 43 мкс проти 13 для свого). Негативний dentry відкидається
  для створення й цілі перейменування, тож нове ім'я має регістр того, хто
  його дав. Перейменування лише регістру (`foo` → `FOO`), яке і з wineserver
  мовчки нічого не робило, ntos робить як Windows: через ім'я поруч.
  Перша версія зробила кожен пошук на томі на 11–20 мкс повільнішим: хеш і
  порівняння викликали `nls->char2uni` на кожну літеру, а непрямий виклик
  (retpoline) дорогий. ASCII тепер береться з таблиці upcase напряму. У VM
  (2026-11-23, те саме ядро з `ntfs.ci_dcache=0` і без): іншим регістром
  14,6 мкс проти 36,9, свій регістр 14,5 проти 13,7, відсутнє ім'я 19,1
  проти 16,2. `ntfs.ci_dcache=0` при завантаженні вимикає це для порівняння.
- **Виміри поруч із Windows.** ntbench проганяється на Windows на тому самому
  ноутбуці; таблиця «Windows / Arctic» для кожного виклику в `docs/ntos.md`.
  Оновлення не йде, поки якийсь виклик повільніший, ніж у Windows, без
  відомої причини.

Де Arctic уже може бути швидшим: планувальник, кеш файлів, мережевий стек і
пам'ять Linux; фонових служб менше.

### Те, що в wineserver робить ОС, у ядрі

| wineserver | ntos |
|---|---|
| головний цикл: epoll, таймаути | `vfs_poll` + черги очікування, hrtimer → робота в черзі ядра під замком |
| дескриптори файлів через сокет | `fget` / `fd_install` у процесі, що викликає |
| `kill`, `tgkill` (APC, призупинення) | `send_sig_info` тому самому потоку — клієнт не змінюється |
| `ptrace`, `/proc/<pid>/mem` | `access_process_vm` |
| inotify | fsnotify |
| memfd, mmap | shmem, `vmap` |
| файли реєстру: fopen, запис, fsync, rename | `filp_open`, `kernel_write`, `vfs_fsync`, `vfs_rename` |
| flock, F_SETLK | блокування VFS |
| сокети: poll, accept, getsockopt | API сокетів ядра над `struct file` клієнта |
| `setpriority`, `sched_*` | `set_user_nice`, `sched_setattr_nocheck` |
| вихід потоку = закритий сокет | виклик із `do_exit` (патч `0007`, як у win32k) |

### Очікування й APC

Клієнт не змінюється: `select` повертає `STATUS_PENDING`, а пробудження ядро
пише в `wait_fd` потоку так само, як wineserver (`kernel_write` у його pipe);
APC будить потік сигналом. Синхронізація об'єктів — ntsync, як зараз
(`inproc_sync`).

### Старт процесу

`new_process` лишається як є: батько робить пару сокетів і віддає свій кінець
виконавчій системі, дитина успадковує другий (`NTSERVERSOCKET`) і віддає його в
`nt_hello(NT_HELLO_PROCESS)`. Ядро шукає процес, чий `msg_fd` — сусід цього
сокета (`unix_peer_get`), і прив'язує задачу до його першого потоку. Процес без
батька в NT (wininit, будь-яка програма, запущена з arctic-init) робить
`nt_hello(NT_HELLO_CONNECT)`, і ядро робить те саме, що робило прийняття на
головному сокеті. Новий потік називає свій id, який дав `new_thread`
(`NT_HELLO_THREAD`). Дескриптори в обидва боки йдуть системними викликами
`nt_send_fd`/`nt_receive_fd`, а не по сокету. Ядро саме підставляє
`unix_pid`/`unix_tid` у `init_first_thread`/`init_thread`: що каже клієнт, не
враховується. Смерть потоку ядро бачить у `do_exit` (`ntos_thread_exit`), а
`exec` у чужу програму — так само, як wineserver: request-pipe закривається.

Запасний шлях: `ENOSYS` (ядро без ntos) або `ENOENT` (`arctic.ntos=0`, або
`nt_boot` не вдався) — ntdll іде до wineserver, як раніше. arctic-init тоді
запускає ntexec (`start_executive`).

### Реєстр

Той самий текстовий формат і ті самі файли на C:, що зараз: міграції немає.
Зберігання — робота в ядрі (черга `ntos-save`), атомарно (новий файл, `fsync`,
`rename`): сирий знімок гілки береться під замком у пам'ять, а текст з нього
робить і пише вже робота, поки виконавча система йде далі (wineserver робив
це дочірнім процесом).
arctic-init перед вимкненням просить зберегти через
`nt_admin(NT_ADMIN_FLUSH_REGISTRY)`; виклик чекає, поки запис закінчиться.
Черги `ntos` і `ntos-save` заморожувані: гібернація чекає, поки збереження
допишеться, і спить разом із програмами, як спав wineserver. Формат кущів
Windows (regf) — окремим кроком після рівності.

### win32k

Callout-и wineserver → win32k (`server/win32k.c`, `W32_CALLOUT_*`) стають
прямими викликами всередині ядра; ntdll більше не перекладає дескриптори
робочих столів на номери через wineserver.

## Перевірка (все — у VM, до оновлення)

1. **Конформанс-тести Wine** — усі, що стосуються виконавчої системи: ntdll,
   kernel32, kernelbase, advapi32, user32, win32u, gdi32, ws2_32, rpcrt4, ole32,
   shell32, msvcrt/ucrtbase (файли), setupapi, ntoskrnl.exe, iphlpapi, winhttp
   (сокети), comctl32, conhost/kernel32 console, dbghelp (налагодження).
   Порівняння: той самий образ з `arctic.ntos=0` і без — однакові набори
   помилок.
2. **ntbench** — нічого не повільніше; виклики `NtClose`, `NtCreateFile`,
   `NtQueryValueKey`, `CreateProcess`, `WaitForSingleObject` у таблиці.
3. **Сценарії VM** (`tests/vm/`): завантаження, вхід, «Пуск», Провідник,
   копіювання файлів, Панель керування, Диспетчер завдань, cmd і PowerShell 7,
   Git, Chrome, IDE на Electron, служби, Bluetooth-сторінка, мережні папки,
   WSL і hamam (дерево процесів у вікні UAC), Rufus, гра на D3D, вимкнення,
   перезавантаження, сон і гібернація, оновлення (`make-update` у VM).
4. **Стрес:** багато потоків і процесів, сокети під навантаженням, канали,
   швидкі `CreateProcess`/`ExitProcess`, падіння процесів посеред запитів.

Оновлення ставиться на залізо лише тоді, коли всі чотири пункти зелені.

Як ганяти (не довше 15 хвилин на прогін): `tests/vm/nb.cmd MODE test:unit…`
(ntbench і юніти зміни, ~2 хв) або `tests/vm/ntall.cmd MODE` (усі набори в
чотири смуги: тести фокуса й буфера обміну одна за одною в першій). Тест пише
`D:\NTSTART.TXT` на старті й `D:\NTDONE.TXT` в кінці; `vm-test.py --until-off
900` читає їх з образу диска, вводить команду ще раз, якщо вона загубилась, і
вимикає VM кнопкою живлення, щойно тести закінчились. ntos і wineserver
порівнюються лише в одній сесії, VM за VM: між днями хост дає ±30 %.

## Робочий процес

- Модуль: `kernel/drivers/ntos` (obj-y, як win32k); каталоги за компонентами
  ntoskrnl: `ob/ ke/ io/ cm/ ps/ se/ mm/ dbgk/ lpc/ dxg/ ex/`.
- Перенесення: `tools/ntuser/port.py` (розширений для ntos), далі вручну до
  0 помилок W=1; перевірка компіляції без повної збірки ядра — як у win32k.
- Wine: патч `0154` (ntdll транспорт, `nt_hello`, файл процесу, arctic-init);
  ядро: патч `0008` (таблиця викликів, вихід потоку).
- Етапи розробки (не поставки): транспорт і Ob → Ke → Io (файли, канали,
  сокети, пристрої) → Cm → Ps/Se → Mm, dxgkrnl, Dbgk, консоль, ALPC → arctic-init
  і arctic-lxss → повний прогін тестів з одним замком (еталон) → дрібні замки
  як у Windows → винятки й APC без сигналів → імена без регістру в ядрі →
  повний прогін тестів і ntbench поруч із Windows → оновлення.
