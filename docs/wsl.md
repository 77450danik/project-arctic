# WSL в Arctic: звичайні дистрибутиви у ВМ, гейт — окремий дистрибутив

У Windows WSL — не двері в систему, а контейнер у віртуальній машині
гіпервізора. В Arctic має бути так само: `wsl` поводиться як у Windows,
дистрибутиви ізольовані від хоста, і їх можна завантажувати й установлювати
тими самими командами. А доступ до самого Linux хоста (root, для збірок
Arctic) — це **окремий наперед установлений дистрибутив**, і лише він за
вікном UAC і паролем (`docs/linux-gate.md`).

Linux від цього на хості не з'являється: ядро ВМ і її initrd — це ядро й
драйвери, як і ядро хоста, а не Linux user mode. Усе, що бачить людина,
програма чи агент, лишається Windows (`docs/linux-gate.md`, вимога 1).

## Напрям (рішення користувача 2026-10-12)

1. **WSL — максимально як у Windows.** Кожен дистрибутив — контейнер зі
   свого `ext4.vhdx`, ізольований від хоста; синтаксис `wsl` один в один;
   дистрибутиви встановлюються й качаються, як там (`wsl --install -d …`,
   `--list --online`, `--import`, `--export`, `--unregister`).
2. **Звичайні дистрибутиви — справжня ВМ через KVM**, як WSL2 буквально, а
   не простір імен на хості.
3. **Стокова WSL від Microsoft** (відкритий код, MIT, MSI з
   `github.com/microsoft/WSL`) **працює без змін**, як будь-яка інша
   програма Windows (`stock-windows-programs`): ми не пишемо свою WSL, ми
   реалізуємо в Arctic те, на чому вона стоїть. Виправляти — Arctic, а не
   програму.
4. **Стокова WSL наперед в образі**: працює без інтернету з першого старту;
   інші дистрибутиви — на вимогу, як у Windows.
5. **Гейт — окрема програма по суті всередині WSL**: один наперед
   установлений дистрибутив (`arctic-build`), який веде не у ВМ, а на хост
   (root). У `wsl -l` він поряд з іншими, і всі прапорці `wsl` працюють для
   нього, як для будь-якого дистрибутива. За UAC і паролем — лише він.
6. **Збірки Arctic — у гейт-дистрибутиві** (`arctic-build`: toolchain,
   `loop`/`mount`/`nbd`/`chroot`). `arctic-ros` (збірка ReactOS) прав не
   потребує і стає звичайним дистрибутивом.
7. **Звичайні дистрибутиви — без UAC**: `wsl` вільний для людей і агентів, як
   у Windows.

## Дві частини

| | Звичайний дистрибутив | Гейт-дистрибутив (`arctic-build`) |
|---|---|---|
| Де працює | утилітарна ВМ (KVM через WinHvPlatform) | хост |
| Ядро | своє, ядро ВМ | ядро хоста |
| Права | root у контейнері, хоста не бачить | root на хості |
| Диск | свій `ext4.vhdx` у ВМ | свій `ext4.vhdx`, `qemu-nbd` на хості |
| Хто веде | стокова WSL (`wslservice`) | наш `arctic-lxss` |
| Питання людині | немає | UAC + пароль, раз на процес і раз на завантаження |
| Де записано, що він гейт | — | `distro=` у захищеному `gate.conf` (`docs/linux-gate.md`) |

## Що Arctic має реалізувати, щоб стокова WSL пішла

| Шар, на який стоїть WSL у Windows | Що це в Arctic | Стан |
|---|---|---|
| `WinHvPlatform.dll` (гіпервізор) | є: KVM під усім API (`docs/hypervisor.md`) | ✅ |
| HCS: `computecore.dll`, `vmcompute.exe` — створення й керування утилітарною ВМ за JSON-документом (`LinuxKernelDirect`: ядро + initrd, virtio-пристрої, пам'ять, vCPU) | наш `computecore` над WinHvPlatform і служба `vmcompute`; документ HCS → машина KVM | ⏳ |
| `hvsocket` (`AF_HYPERV`), яким `wslservice` говорить з гостем | своє сімейство сокетів у `afd`/`ws2_32` над `AF_VSOCK` KVM (ідентифікатори служб HCS → порти vsock) | ⏳ |
| Ядро гостя й initrd (у MSI — `C:\Program Files\WSL\tools`) | стокові, з MSI; наше ядро — тільки для хоста | ⏳ |
| Диски Windows у гості (`/mnt/c`): WSL віддає їх по 9P/virtio-fs | сервер на хості, під'єднаний до ВМ як virtio-пристрій, що описує документ HCS | ⏳ |
| Мережа: NAT за замовчуванням | `tap` + NAT у `arctic-init`, як адаптер ВМ у документі HCS; DNS — наш `resolvconf` | ⏳ |
| Реєстр `HKCU\Software\Microsoft\Windows\CurrentVersion\Lxss`, служби `WslService`/`vmcompute` | ключі заводить сама WSL; від нас — щоб `services.exe` підняв її службу, як у Windows | ⏳ |
| `wsl.exe`, `wslservice.exe`, `wslg` | стокові, без змін | ⏳ |

Поки цього немає, усі дистрибутиви веде `arctic-lxss` (root-chroot на хості).
Це тимчасово й це обхід гейта для звичайних дистрибутивів — користувач на це
погодився 2026-10-12, доки ВМ не працює.

## Гейт усередині WSL

`wslservice` стокова, і вона нічого не знає про хост: відвести один
дистрибутив на хост вона не вміє, а плагіни WSL такого теж не дають. Тому
двері — там, де їх і ставить сама Windows, у `System32\wsl.exe`:

- У Windows 11 `System32\wsl.exe` — тонкий переадресник до
  `C:\Program Files\WSL\wsl.exe`. Наш переадресник робить те саме, а перед
  тим дивиться, чи йдеться про гейт-дистрибутив (ім'я з захищеного
  `gate.conf`, не зі списку, який може переписати будь-хто): якщо так — до
  `arctic-lxss` під UAC і паролем; якщо ні — стоковій WSL, без змін і без
  питань.
- `wsl -l`, `-l -v`, `--list --online` — список стокової WSL плюс рядок
  гейт-дистрибутива; `--shutdown` гасить ВМ і лишає гейт, `-t <гейт>`
  відчіплює його VHDX.
- `System32\bash.exe` — так само (у Windows це запуск дистрибутива за
  замовчуванням).
- Гейт-дистрибутив **не реєструється** в `Lxss`: інакше стокова
  `wslservice` спробувала б підняти його у ВМ.

## Перевірка (QEMU, `tools/vm-test.py`)

1. `wsl --version` — версії стокової WSL і ядра, як у Windows.
2. `wsl -l -v` — `arctic-build` поряд зі звичайними дистрибутивами.
3. `wsl -d arctic-build -- uname -a` → UAC + пароль, далі ядро **хоста**.
4. `wsl -d <звичайний> -- uname -a` → ядро **ВМ**, без жодного вікна.
5. `wsl --install -d Ubuntu` (з мережею) ставить дистрибутив; він
   запускається у ВМ.
6. `/mnt/c` у звичайному дистрибутиві читає C:, `ping` і DNS працюють.
7. `wsl --shutdown` гасить ВМ; наступний `wsl` її піднімає; гейт
   відчіпляється окремо (`-t arctic-build`).
8. Збірка Arctic із гейт-дистрибутива (`ci/build-rootfs.sh`) проходить, як
   досі.
