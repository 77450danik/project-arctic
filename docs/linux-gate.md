# Linux лише через WSL: вето, UAC і пароль

Arctic — система Windows. Linux у ній — ядро й драйвери, а все, що бачать
людина й програми, — Windows. Окремої «другої системи» Linux поряд немає:
до самого середовища Linux доступ лише командою `wsl` (і `bash.exe` у
System32, як у Windows 10), і щоразу з дозволу людини — вікном контролю
облікових записів у стилі Windows 7 і, за замовчуванням, паролем.

Гейт — це **один дистрибутив WSL**, а не весь WSL. Звичайні дистрибутиви,
як і у Windows, живуть у віртуальній машині й нікого ні про що не питають;
окремий, наперед установлений дистрибутив (`arctic-build`) — це двері до
самого ядра хоста (root), і саме він за UAC і паролем. Яким має бути весь
WSL — `docs/wsl.md`; тут — лише гейт.

Доки звичайні дистрибутиви ще не у ВМ, вони теж root-chroot на хості
(`docs/updates.md`, етап 2): тимчасовий обхід гейта, на який користувач
погодився 2026-10-12.

## Вимоги (2026-10-11)

1. Жоден компонент Linux не використовується напряму: ні людиною, ні
   програмами, ні агентами (Claude Code та іншими). Усі інструменти —
   Windows-версії (git, gh, PowerShell, node…).
2. Linux — тільки через `wsl.exe` / `System32\bash.exe`.
3. Вхід у Linux захищено паролем; змінюється в Панелі керування
   («Облікові записи користувачів»). Початковий пароль `0000`.
4. Пароль вводиться **раз на завантаження**: після першого правильного
   введення до перезавантаження його більше не питають.
5. Вікно UAC (стиль Windows 7, «для підтвердження цієї дії потрібні права
   адміністратора») з'являється **раз на процес/вікно**: перша програма чи
   термінал, що просить Linux, — питання; її дочірні процеси — без питань.
6. Пароль можна вимкнути: тоді лишається тільки підтвердження «Так/Ні».
7. Агенти — як на Windows: працюють через PowerShell/cmd вільно, а Linux
   для них — така сама дія адміністратора через той самий гейт.
8. Релізний образ без консолі Linux; dev-консоль `ttyS0` (лише
   `arctic.dev=1`) — теж за паролем.
9. Кожна зміна потрапляє **і в новий образ, і в уже встановлену систему
   пакетом оновлення** (етапи 1–3 `docs/updates.md`, з відкатом).
10. Робота системи не погіршується.
11. Сумісність — з Windows 10: що працює у Windows 10 (Git Bash і все
    на MSYS2/Cygwin, gh, PowerShell, IDE з їхніми терміналами), має
    працювати й тут. Несумісність виправляється в самій системі (Wine,
    ReactOS), а не обходиться.

## Що є зараз

| Двері в Linux | Хто ними користується | Захист |
|---|---|---|
| `arctic-lxss` (root, 127.0.0.1, токен із `C:\ProgramData\Arctic\Lxss\session`) | `wsl.exe`, `bash.exe`, `git.exe`, `sh.exe` (одна програма Wine) | токен читає будь-який процес Windows → root у дистрибутиві |
| `CLAUDE_CODE_GIT_BASH_PATH=C:\Windows\System32\bash.exe` (`runtime/registry/wsl.reg`) | інструмент Bash у Claude Code | немає: кожна команда агента — у Linux |
| `C:\Windows\System32\git.exe` на PATH | усі, хто кличе `git` | немає: це git дистрибутиву |
| серійна консоль `ttyS0` (`arctic-init.c`, лише dev) | розробник | немає |

## Модель доступу

```
програма (claude.exe, cmd.exe, …)
  └─ wsl.exe / bash.exe ── TCP 127.0.0.1 ──► arctic-lxss (root)
                                               │ 1. хто це? /proc/net/tcp → pid → предки
                                               │ 2. у когось із предків є дозвіл? → виконати
                                               │ 3. ні → служба Appinfo, чекати відповіді
                                               │      пароль цього завантаження ще не введено
                                               │      і пароль увімкнено → поле пароля
                                               │ 4. «Так» (+ правильний пароль) → дозвіл
                                               │      процесу-джерелу, виконати
                                               └ 5. «Ні» → «Операцію скасовано користувачем.»

   arctic-lxss (root) ── TCP 127.0.0.1 ──► svchost.exe -k netsvcs
                                             └ appinfo.dll (служба «Application
                                               Information», брокер UAC)
                                                 └ consent.exe (вікно UAC)
```

**Вікно показує служба, а не root.** Як у Windows: єдине, що ставить вікно
UAC на екран, — служба Appinfo (`appinfo.dll` у `svchost.exe`), а не той, хто
просить прав. root сам не запускає жодної програми Windows: він стукає до
служби на 127.0.0.1 і передає їй рядки протоколу. Служба нічого не вирішує —
пароль перевіряє root, дозвіл записує root. Так увесь UAC (вигляд вікна, DPI,
звук, «безпечний робочий стіл») — це код Windows у сеансі, а брокер підвищення
прав — в одному місці, куди далі ляже `RAiLaunchAdminProcess` для `runas` і
програм з `requireAdministrator`.

- **Рішення приймає root.** `arctic-lxss` лежить у `host.sqfs` (тільки
  читання) і працює від root: процес Windows (усі вони — користувач `nt`)
  не може його підмінити, вбити чи прочитати його пам'ять.
- **Хто питає, визначає сервер, а не клієнт.** За локальним портом
  з'єднання (`/proc/net/tcp`, inode сокета в `/proc/<pid>/fd`) знаходиться
  процес, далі — його предки (`/proc/<pid>/stat`). Процеси Wine — звичайні
  процеси Linux, тож дерево справжнє; підробити «я — дозволений процес»
  не вийде. Старий `wsl.exe` працює без змін протоколу — він просто
  потрапляє під гейт.
- **Дозвіл** — пара (pid, час старту) процесу-джерела: повторне
  використання pid дозволу не успадковує. Таблиця дозволів і прапорець
  «пароль цього завантаження введено» — у спільній пам'яті
  (`MAP_SHARED` до `fork` кожного з'єднання), лише в пам'яті: перезавантаження
  все скидає.
- **Процес-джерело** — найближчий предок, що не є `wsl.exe`/`bash.exe`.
  Якщо це системний процес (`explorer.exe`, `svchost.exe`, `services.exe`,
  `winlogon.exe`, `wininit.exe`, `csrss.exe`, `rpcss.exe`, `winedevice.exe`,
  `wineserver`, `arctic-init`), дозвіл отримує сам `wsl.exe` (вікно, яке
  він відкрив): інакше ярлик у «Пуску» дав би Linux усьому, що запускає
  Провідник. Системні процеси дозволів не отримують ніколи.
- **Усередині дистрибутиву** (процес, чий `/proc/<pid>/root` — під
  `/run/lxss/`) — уже Linux: `tools/arctic/wsl.py` у збірках ходить без
  питань.
- **Одне вікно UAC за раз** (`flock`), як у Windows. Запити, що чекали,
  після відповіді перевіряють дозвіл знову: два `bash.exe` одного агента
  дають одне питання.
- Без відповіді 2 хв — «Ні». Після 5 неправильних паролів поспіль —
  пауза 30 с.
- Під гейтом усе, що торкається Linux: команди, оболонка, `--shutdown`,
  `-t`. Без гейта — лише `wsl -l` (читає файл на C:).

Як і UAC у Windows, це межа згоди, а не пісочниця: програма, якій уже
дозволили Linux, — root у дистрибутиві. Те, що гейт зупиняє: будь-яку
програму чи агента, яким людина Linux не дозволяла, і зміну налаштувань
гейта без пароля.

## Де живе пароль

C: змонтовано з `uid=nt` (`arctic-volume.c`): **будь-який процес Windows
може переписати будь-який файл на C:**. Файл з паролем на C: нічого б не
захищав. Тому:

- Стан гейта — у `C:\Windows\System32\config\Host\Gate\` (поряд з іншим
  станом хоста, що переживає оновлення й переустановлення образу).
- `arctic-init` одразу після монтування C: і **до старту wineserver**
  прив'язує цю теку в `/run/arctic/gate` (`0700`, root) і накриває
  оригінальний шлях порожнім tmpfs тільки для читання. Процеси Windows цієї
  теки не бачать і дістатися до неї не можуть: зняти монтування — лише
  root, сирий пристрій диска — лише root.
- `gate.conf`: `password=on|off` і хеш `yescrypt` (`$y$…`, libxcrypt, як
  `/etc/shadow`) з сіллю. Пароль ніде не лежить відкритим текстом.
- Немає файлу (перший старт, нова установка) → пароль увімкнено, `0000`.

Той самий захист варто дати й `/var/lib/iwd` (паролі Wi-Fi, теж у
`config\Host`) — окремою задачею.

## Компоненти

### 1. `host/init/gate.c`, `gate.h` (новий, спільний)

Читання й запис `gate.conf`, перевірка пароля (`crypt_rn`), новий хеш
(`crypt_gensalt_rn("$y$")`). Компілюється в `arctic-lxss` і `arctic-init`
(`-lcrypt`, `ci/build-rootfs.sh`).

Буфер для `crypt_gensalt_rn` — `CRYPT_GENSALT_OUTPUT_SIZE`, не менше: з 64
байтами libxcrypt повертає `ERANGE` і хеша не робить зовсім, а порожній хеш
означає, що **жоден пароль не підходить**. Саме так і було: вікно брало
правильний `0000` і щоразу писало «Неправильний пароль» (знайдено у VM
2026-10-12).

### 2. `host/init/arctic-lxss.c`

- Спільна пам'ять: прапорець пароля, таблиця дозволів (до 256).
- `peer_pid()`: локальний/віддалений порт з'єднання → inode у
  `/proc/net/tcp` → pid.
- `authorized()`: обхід предків; `origin()`: вибір процесу-джерела.
- `ask_consent()`: з'єднання до служби Appinfo (порт і токен із
  `C:\ProgramData\Arctic\Appinfo\session`) і рядковий діалог через нього:
  `prompt <пароль 0|1> <ім'я програми> <шлях> <що просять>` → `yes <пароль>` /
  `no` → `ok` / `wrong` (вікно лишається, «Неправильний пароль») /
  `wait <секунди>`. Сам root вікон не запускає.
- **Чи це справді служба.** Файл `session` лежить на C:, яку будь-який процес
  Windows може переписати: тому процес на іншому кінці з'єднання має бути
  `svchost.exe`, запущений `services.exe` (дерево процесів wineserver, патч
  `0090`). Інакше — ні вікна, ні дозволу: запис у журнал і відмова. Без цього
  програма підсунула б замість служби власне вікно, що просить пароль Linux.
  Сокет Wine тримає **не один процес**: wineserver робить його й передає
  програмі, тож за inode з `/proc/net/tcp` знаходяться обидва. Беруться всі
  власники, wineserver пропускається (він тримає сокети всіх), а поки жоден
  інший його ще не взяв — чекається (`is_appinfo_service`). Перший варіант
  брав першого власника й бачив `wineserver`: вікна не було, а `wsl` казав
  «Операцію скасовано користувачем» (знайдено у VM 2026-10-12).
- Якщо служби ще немає (перші секунди завантаження) — чекає до 20 с, як будь-яка
  програма чекає службу.
- Новий запит `REQ_GATE` (для Панелі керування): стан; змінити пароль;
  увімкнути/вимкнути пароль. Завжди питає UAC з **поточним** паролем (якщо
  він увімкнений), незалежно від дозволів, — як зміна параметрів UAC у
  Windows.

### 3. `runtime/wine/modules/dlls/appinfo` → `appinfo.dll` (новий)

Служба «Application Information» (Appinfo) — брокер UAC, як у Windows: DLL
служби в `svchost.exe -k netsvcs` (`runtime/registry/uac.reg`: служба
`Appinfo`, `ServiceDll`, група `netsvcs`, політики
`HKLM\…\Policies\System` — `EnableLUA` та інші, які читають інсталятори).

- Слухає 127.0.0.1 на випадковому порті, токен — 16 випадкових байтів;
  порт і токен пише в `C:\ProgramData\Arctic\Appinfo\session`.
- На запит: **одне вікно за раз** (`Global\ArcticAppinfoConsent`), запуск
  `System32\consent.exe` з `WINEDLLOVERRIDES=consent.exe=b` — вікно завжди
  вбудоване з образу хоста, навіть якщо файл на C: підмінили, — і передача
  рядків між трубами вікна й з'єднанням хоста.
- Служба не бачить ні `gate.conf`, ні пароля й нічого не вирішує: програма,
  що з'єдналася сюди сама, може лише змусити з'явитися вікно — те саме, що
  дає виклик власного API підвищення прав у Windows.
- У Windows ця служба — `DEMAND_START` (її будить API підвищення прав). Тут
  просить root, а root не може звернутися до диспетчера служб, тому служба
  `AUTO_START` — єдине відхилення від Windows, решта (ім'я, група,
  `ServiceDll`) як там.
- Далі тут же: `RAiLaunchAdminProcess` для `runas` і манифестів
  `requireAdministrator`, тобто повноцінний UAC для програм Windows.

### 4. `runtime/wine/modules/programs/consent` → `consent.exe` (новий)

Вікно контролю облікових записів. Лише вікно: нічого в системі не просить і
нічого не вирішує. Його запускає служба Appinfo зі своїми стандартними
дескрипторами на трубах і говорить із ним тими самими рядками
(`prompt` → `yes <пароль>` / `no` → `ok` / `wrong` / `wait <секунди>`).

**Це звичайне вікно системи**, а не намальоване: шаблон `DIALOGEX`, рамка й
заголовок — теми (msstyles), контроли — системні (манифест просить
`Microsoft.Windows.Common-Controls` 6.0). Перший варіант малював свій синій
заголовок, своє тіло й чорну «затемнену» підкладку — від цього відмовилися
2026-10-12: у Windows 7 це теж звичайне вікно, і малювати його руками не
треба.

- щит, «Для підтвердження цієї дії потрібні права адміністратора.»;
- «Програма: Підсистема Windows для Linux», «Перевірений видавець: Project
  Arctic», «Запит від: <програма-джерело>»; кнопка «Показати подробиці» —
  повний шлях і команда;
- поле пароля (лише коли сервер його просить) і рядок «Введіть пароль
  підсистеми Linux і натисніть «Так»»; «Неправильний пароль.» під полем,
  місце під нього лишається завжди, щоб вікно не стрибало між спробами;
- «Так» / «Ні», Enter, Esc, звук `Windows User Account Control`;
- вікно — у смузі поверх вікон програм (`SetWindowBand`, Wine `0041`).
  Затемнення робочого столу, як у Windows, поки немає: шарове вікно над
  столом виходить чорним, а не притемненим.
- Те, що не потрібне цьому запиту (подробиці, пароль, повідомлення),
  сховано, а решта піднімається на його висоту — уся розкладка.

### 5. `runtime/wine/modules/programs/wsl`

- Лишаються `wsl.exe` і `System32\bash.exe` (у Windows обидва — запуск
  WSL). `git.exe` і `sh.exe` під цим іменем зникають: git — це Git for
  Windows.
- Відмова сервера → «Операцію скасовано користувачем.», код 1, як у
  Windows.

### 6. Панель керування: «Облікові записи користувачів»

- `dlls/usercpl` — пункт Панелі керування Windows 7
  ({60632754-C523-4B62-B45C-4172DA012619}, `uac.reg`), сторінка «Внесення
  змін до облікового запису користувача» на спільному вигляді Панелі
  (`PARENTSRC = ../systemcpl`, `cpanel.c`/`cpfolder.c`, як у `netcenter`):
  обліковий запис із плиткою (значок — Windows'ів, із
  `SystemResources\usercpl.dll.mun`), далі розділ «Підсистема Windows для
  Linux» і посилання зі щитом «Змінити пароль підсистеми Linux» і «Змінити
  параметри контролю облікових записів користувачів» — обидва відкривають
  `UserAccountControlSettings.exe`. Усе, що Windows має для інших облікових
  записів, тут не потрібне: обліковий запис один.
- `programs/useraccountcontrolsettings` → `UserAccountControlSettings.exe`:
  вікно Windows 7 (біле тіло з синьою інструкцією, сірий низ із «OK» і
  «Скасувати»), розділ «Підсистема Windows для Linux»:
  - ☑ «Вимагати пароль для доступу до Linux»;
  - «Змінити пароль…» — новий і підтвердження; **поточний** питає вікно UAC,
    бо перевіряє його тільки root;
  - пояснення: пароль питається раз після кожного перезавантаження,
    дозвіл — раз на програму;
  - щит на «OK» і «Змінити пароль…» (`BCM_SETSHIELD`), як у Windows на всьому,
    що веде до підвищення прав.
  Застосування — `REQ_GATE` (`gate.c`/`gate.h` програми: ті самі кадри, що в
  `wsl.exe`), тобто через вікно UAC; відмова — «Операцію скасовано
  користувачем.» і параметри лишаються як були.

### 7. `host/init/arctic-init.c`: dev-консоль

`ttyS0` (лише `arctic.dev=1`): перед оболонкою «Пароль підсистеми
Linux:» (`gate.c`); якщо пароль вимкнено — «Натисніть Enter, щоб
підтвердити». Три помилки — 30 с паузи. У релізі консолі немає, як і досі.

### 9. Інструмент Bash у Claude Code

Мета — справжній Git Bash (`C:\Program Files\Git\bin\bash.exe`), як у
Windows. **Зараз він під Arctic не працює:** сам bash іде, але будь-яка
зовнішня команда зсередини нього — `Bad address` (запуск дочірнього
процесу рантаймом MSYS2/Cygwin у Wine), і `Couldn't compute FAST_CWD
pointer`. `uname.exe`, запущений прямо з Windows, працює. Потрібен патч
Wine (`runtime/wine/patches`) — окремий етап із тестом
`tests/vm/w8-git-bash.txt` (fork, конвеєри, `mktemp`, `git` з bash, коди
виходу).

**Рішення 2026-10-11: агенти — як у Windows одразу, без перехідного
періоду.** `CLAUDE_CODE_GIT_BASH_PATH` із системного оточення зникає
(`runtime/registry/wsl.reg`): Claude Code, як у Windows, сам знаходить Git
Bash за встановленим Git for Windows, а поки той не працює — працює через
PowerShell. Linux для агента — лише явний `wsl …` під гейтом, як у
Windows 10. Перевірено 2026-10-11 у живій системі: PowerShell 7,
`git.exe` і `gh.exe` для Windows (status, log, commit, fetch, push) — без
Linux.

Пастка, знайдена тоді ж: `gh auth setup-git` кличе `git` з PATH, а там
`System32\git.exe` — міст у Linux, тож налаштування лягло в `.gitconfig`
дистрибутиву. Ще одна причина прибрати міст (етап 4).

### 10. Хост без Linux user mode (вимога 2026-10-11)

Від Linux лишаються ядро, модулі, прошивки й **драйвери користувацького
режиму** — те, що у Windows є UMD: Mesa, NVIDIA userspace, Vulkan-завантажувач,
alsa-lib з UCM, libinput/libevdev, бібліотеки unix-частини Wine. Плюс наші
власні програми хоста (`arctic-*`) і сам Wine (`wineserver`, завантажувач).
Утиліт, оболонок і «системи» Linux на хості немає. Рішення 2026-10-11 —
**етапно**:

| Що зараз викликає хост | Чим замінюється | Етап |
|---|---|---|
| `pacstrap` усього списку пакетів | замикання ELF-залежностей наших програм + allowlist даних (як і задумано в `PLAN.md`, розділ 5) | 11 |
| `busybox ip` (адреси, маршрути) | netlink у `arctic-init` | 12 |
| `busybox udhcpc` + `udhcpc.script` | власний DHCP-клієнт (`host/init/dhcp.c`); пізніше — служба `Dhcp` у Windows-світі через hostd | 12 |
| `amixer`, `alsactl init` | alsa-lib mixer API в `arctic-init` | 13 |
| `modprobe`, `modinfo` (kmod) | libkmod у `arctic-init`, `arctic-gpu`, `arctic-lxss`, `arctic-smb` | 13 |
| `udevadm trigger` | запис `add`/`change` у `/sys/.../uevent` самим `arctic-init` | 13 |
| `busybox sh` на `ttyS0` (dev) | dev-консоль лишається лише в dev-образі, за паролем (розділ 7); у звичайному образі busybox немає. Налагодження живої системи — через WSL (дистрибутив бачить хост через `/proc/1/root`), теж під гейтом | 14 |
| `/bin/sh`, `/bin/bash` у `arctic-lxss` | беруться з дистрибутиву (chroot), хосту не потрібні | 14 |
| `systemd-udevd` + hwdb | **лишається** невидимим бекендом (PnP); власний менеджер пристроїв — окремий етап після цього плану | — |
| `iwd` + `dbus-daemon` | **лишаються** невидимими бекендами Wi-Fi; власний WPA у `Wlansvc` — окремий етап | — |
| `qemu-nbd` | частина WSL: стартує лише `arctic-lxss` для дистрибутиву | — |

Збірка образу (`mkprefix.sh`, `register.sh`) і далі йде в контейнері з
busybox, але busybox не потрапляє в `host.sqfs`. Перевірка етапу 11:
`unsquashfs -l host.sqfs` без `bin/sh`, `busybox`, `coreutils`, `pacman`,
`python`; усе з таблиці `PLAN.md` 4 працює у VM.

## Перевірка (QEMU, `tools/vm-test.py`, диск як після встановлення)

1. Перший `wsl -e id` після старту → UAC з паролем; `1111` → «Неправильний
   пароль»; `0000` → `uid=0`.
2. Той самий cmd.exe: `wsl -e id` ще раз — без вікна.
3. Новий cmd.exe → UAC **без** поля пароля; «Ні» → «Операцію скасовано
   користувачем.», код 1.
4. Процес, що дістав токен і стукає в arctic-lxss сам, — вікно називає
   саме його.
5. Вікно належить службі: доки воно на екрані, `tasklist` показує
   `svchost.exe` і `consent.exe`; `sc stop Appinfo` → `wsl -e id` відмовляє
   («служба не відповіла») і не вішається.
6. Підробка брокера: програма пише свій порт і токен у
   `C:\ProgramData\Arctic\Appinfo\session` і слухає його → гейт відмовляє,
   у журналі «is not the Application Information service», вікна немає.
7. Пароль вимкнено в Панелі керування (через UAC з `0000`) → після
   перезавантаження лише «Так/Ні».
8. Новий пароль → `0000` більше не підходить; перезавантаження —
   питається раз.
9. `dir C:\Windows\System32\config\Host\Gate` з Windows — порожньо;
   запис туди — відмова.
10. Агент: інструменти Bash (Git Bash) і PowerShell без жодного вікна;
    `wsl …` від агента → одне вікно на процес агента.
11. `wsl.py` з дистрибутиву (збірка) — без вікон.
12. dev-образ: `ttyS0` питає пароль; реліз: консолі немає.
13. `git`, `gh`, `powershell.exe` з cmd — Windows-версії
    (`where git` → `C:\Program Files\Git\cmd\git.exe`).
14. Пакет оновлення на встановлений диск → усе вище; потім
    `arctic.rollback=1` → попередній стан, `System32\git.exe` повернувся.
