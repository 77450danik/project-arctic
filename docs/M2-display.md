# M2 — екран у Панелі керування: робочі нотатки

Як роздільність і частота оновлення доходять від `desk.cpl` до монітора, і що
для цього додано. Документ робочий: оновлюється, поки йде M2.

## Шлях зміни режиму

```
desk.cpl → ChangeDisplaySettingsEx(1280x800@75, CDS_UPDATEREGISTRY)
  → win32u: apply_display_settings → pChangeDisplaySettings
    → winewayland.drv: arctic_configuration_v1 (режим і позиція кожного монітора)
      → dwm.exe: kms_apply → DRM_IOCTL_MODE_SETCRTC
        → монітор перемикається, dwm розсилає нові події wl_output
      ← succeeded
    ← win32u: перечитує пристрої, WM_DISPLAYCHANGE усім вікнам
```

Зворотний напрямок (перелік пристроїв) — `pUpdateDisplayDevices`: список
моніторів з `wl_output`, позиції з `xdg_output`, EDID і відеоадаптер — з
`arctic_display_v1`.

## Що додано

| Частина | Де | Що робить |
|---|---|---|
| `kms.c` | dwmcore (unix) | усі підключені конектори картки, EDID, списки режимів, зміна режиму з відкатом, гаряче підключення через uevent |
| `compositor.c` | dwmcore (unix) | по `wl_output` на монітор, `xdg_output` з позиціями й назвами, `arctic_display_v1`, композиція у віртуальний екран і копія в буфер кожного монітора |
| `dwmcore.c` | dwmcore (PE) | політика: збережена розкладка для цього набору моніторів, інакше рідна роздільність і найвища частота; збереження в реєстр |
| патч `0029` | winewayland.drv | `arctic_display_v1` у клієнта: EDID, адаптер, `ChangeDisplaySettings` |
| патч `0030` | win32u | монітор з EDID — «Generic PnP Monitor», як у Windows |
| `desktop.c` | winsrv (csrss) | вікна з від'єднаного монітора повертаються на екран; про гаряче підключення дізнаються всі програми |
| патч ReactOS `0013` | desk.cpl | частота оновлення під роздільністю, усі режими монітора, назва моделі з EDID, справжні позиції моніторів |
| патч `0031` | win32u | робоча область належить екрану: після зміни режиму вона забувається |
| патч ReactOS `0014` | shell32 | робочий стіл стежить за `WM_DISPLAYCHANGE` (у Windows його змінює win32k) |
| патч ReactOS `0015` | desk.cpl | перетягування моніторів: кинутий монітор лишається на новому місці й «Застосувати» переносить його насправді |
| `dispmode.exe` | programs/dispmode | тестова програма: список пристроїв і режимів, зміна режиму з консолі |

Панель дисплеїв у системі одна — з ReactOS: власну `desk.cpl` Wine (параметри
віртуального робочого столу) з образу прибрано, інакше завантажувач брав її.

## Правила, за якими вибирається режим

- **Перше завантаження:** рідна роздільність монітора (`DRM_MODE_TYPE_PREFERRED`)
  і **найвища частота**, яку монітор на ній тримає. Якщо `SETCRTC` не пройшов
  (кабель не тягне), береться наступна нижча частота, далі — режим, який монітор
  називає рідним.
- **Далі:** якщо для цього набору моніторів є збережена розкладка
  (`HKLM\SYSTEM\CurrentControlSet\Control\GraphicsDrivers\Configuration\<набір>`),
  вона має перевагу — там лежить вибір користувача, як у Windows.
- **Зберігається** лише те, що програма застосувала з `CDS_UPDATEREGISTRY`
  (саме так робить Панель керування). Повноекранна гра міняє режим без цього
  прапорця, і після неї повертається збережений.
- **Другий монітор** стає праворуч від наявних зі своєю рідною роздільністю
  («розширити», як за замовчуванням у Windows); монітори, які вже щось
  показують, не чіпаються.
- Основний монітор завжди в точці 0,0 віртуального екрана: win32u рахує
  координати вікон саме від нього.

## Режими, які бачить Windows-сторона

- Тільки прогресивні: черезрядкові й `DBLSCAN` відкидаються.
- Один запис на розмір і цілу частоту: 59,94 Гц і 60,00 Гц — це один «60 Гц»
  (`DEVMODE` носить цілі герци). Точна частота лишається в dwm і йде в KMS.
- Частота рахується з таймінгів (`clock / (htotal * vtotal)`), а не з `vrefresh`.
- **Масштабовані режими, як у драйверів Windows (GPU scaling):** до списку
  додаються стандартні розміри, менші за рідний (640x480, 800x600, 1024x768,
  1280x720, 1280x768, 1366x768, 1600x900 …), з таймінгами рідного режиму й
  на його частоті. Матриця ноутбука (eDP) сама дає лише один режим, і ігри,
  що просять 800x600 чи 1280x768 на весь екран (NFS Hot Pursuit: «Cannot
  start the graphics device»), отримували `DISP_CHANGE_BADMODE`. Кадр такого
  режиму меншого розміру, і площина KMS розтягує його на таймінги монітора зі
  збереженням пропорцій, по центру («maintain aspect ratio»); якщо площина
  так не вміє — на весь екран. Перемикання між ним і рідним не робить
  modeset: матриця не блимає. Картка, що не масштабує площину (немає atomic,
  нема скейлера), такого режиму не отримує: `ChangeDisplaySettings` перевіряє
  це тестовим atomic-комітом (`kms.c`, `add_scaled_modes`, `test_scaling`).

## Перевірка без Панелі керування

`dispmode.exe` у dev-збірці (serial-shell):

```
chpst -u nt env WINEPREFIX=/run/nt HOME=/run/nt/home USER=User \
    XDG_RUNTIME_DIR=/run/nt/xdg WAYLAND_DISPLAY=arctic-0 wine dispmode.exe ...
```

| Аргумент | Що робить |
|---|---|
| (немає) | пристрої, монітори, поточний режим і всі режими |
| `1024x768@60` | перемкнути (з `CDS_UPDATEREGISTRY`, як Панель керування) |
| `restore` | повернути збережений режим |
| `windows` | вікна верхнього рівня в z-порядку: де стоять оболонка й панель задач |
| `broadcast` | сказати всім вікнам, що екран змінився |

Другий монітор у QEMU: `python tools/vm-test.py --monitors 2` (virtio-gpu
замість std VGA); знімок його екрана —
`python ci/qmp-shot.py tcp:127.0.0.1:4455 out/test-local/m2.ppm out/test-local/m2.png 1`.

## Перевірено в QEMU (2026-09-23)

- Завантаження: dwm сам бере рідну роздільність монітора і найвищу частоту на
  ній — 1280x800@75 з EDID, який дає QEMU.
- Панель дисплеїв ReactOS: «Дисплей: QEMU Monitor на Microsoft Basic Display
  Adapter», під роздільністю — «Частота оновлення екрана: 75 Гц».
- Зміна роздільності повзунком → «Застосувати» → «Зберегти ці параметри
  відображення?» з відліком 15 с: екран реально перемикається на 1024x768@60,
  панель задач і робочий стіл переїжджають, «Ні» (чи мовчання) повертає режим.
- Два монітори (`--monitors 2`): dwm ставить їх поруч (0,0 і 640,0), робочий
  стіл 1280x480, кожен зі своїм буфером.

## Перевірено в QEMU (2026-09-26)

Перетягування моніторів, `tests/vm/m2-layout.txt` на `--monitors 2`:

- Кинутий монітор лишається там, де його поклали, «Застосувати» стає активним.
- Після «Застосувати» монітори реально міняються місцями:
  `dwm: Virtual-2 640x480@75 at -640,0` замість `at 640,0` — основний лишився
  в 0,0, а другий переїхав ліворуч.
- Прямокутники стають упритул без щілини, якої не було в кинутому положенні:
  це `place_all_displays` присунув, а сторінка перечитала справжні позиції.
- «Застосувати» знову гасне: `InitialPosition` оновився.

## Як переноситься монітор

Контрол вибору моніторів у desk.cpl завжди вмів тягати прямокутник, але на
відпускання кнопки викидав його: `MonSelCancelDragging` повертав монітор на
місце й нікому нічого не казав. Тепер кинутий монітор лишається там, де його
поклали, а сторінка дізнається про це новим повідомленням.

```
перетягування в desk.cpl → MSLN_MONITORSMOVED (позиція в координатах монітора)
  → сторінка запам'ятовує її на пристрої, «Застосувати» стає активним
    → «Застосувати»: кожному пристрою ChangeDisplaySettingsEx(CDS_NORESET)
      → один ChangeDisplaySettingsEx(NULL, NULL) — усі екрани разом
        → win32u: place_all_displays присуває монітори без щілин,
          основний тримає в 0,0 → драйвер → dwm → KMS
    ← сторінка перечитує позиції: система могла обрати не ті, що просили
```

`CDS_NORESET` тут обов'язковий: без нього кожен монітор переїжджав би окремо і
проміжні розкладки встигали б накластись. Позиція, порахована з кинутого
прямокутника, через цілочисельне ділення буває на пару пікселів іншою —
`place_all_displays` усе одно присуває монітори впритул, тому сторінка після
застосування питає систему, де вони насправді стали.

## Пастка в заголовках ReactOS

Структури API конфігурації дисплеїв (`DISPLAYCONFIG_*`) містять переліки, де
поряд стоять від'ємні значення і `0xFFFFFFFF`. MSVC тримає такий перелік у
чотирьох байтах, GCC — у восьми, тож зібрана з тих заголовків структура не
збігається з тією, яку читає система: `size` опиняється не там, і виклик
відхиляється без жодного повідомлення. Тому `dll/cpl/desk/monitorname.c`
описує ці структури сам і перевіряє розміри через `C_ASSERT`.

## Масштабування менших режимів (гра в 4:3)

Режим, менший за рідний монітора (гра в 1024x768 на 1920x1080), dwm показує
на рідних таймінгах, а масштабує картинку площина карти (`add_scaled_modes`,
`mode_view` у `dwmcore/kms.c`). Як саме — у Windows вирішує панель драйвера
відеокарти, якої в Arctic немає, тож вибір на сторінці «Параметри» панелі
«Екран» (ReactOS `0074`), для кожного монітора:

| Пункт | `Scaling` (DISPLAYCONFIG_SCALING) | Як показано |
|---|---|---|
| Зберігати пропорції (типово) | 4 | якомога більше, з чорними смугами по боках |
| На весь екран | 3 | розтягнуто на весь екран |
| Без масштабування | 2 | піксель у піксель посередині |

Значення лежить у ключі монітора `HKLM\...\GraphicsDrivers\MonitorDataStore\<PnP id>`,
поряд із `VariableRefresh`. dwm стежить за ключем і перемикає на ходу, без
modeset, навіть посеред гри (`kms_set_scaling`); якщо площина так не вміє
(`TEST_ONLY` відмовляє), береться «зберігати пропорції», потім «на весь екран».

Режим гри — лише поки гра попереду, як DXGI тримає його у Windows: коли
вперед виходить інша програма чи гру згорнуто, csrss (`winsrv/desktop.c`,
потік відновлення режиму) повертає збережені режими робочого столу, а коли
гра повертається — її режим. Гра часто робить це сама, але SDL і DXVK у CS2
кожен пам'ятають свій режим, і 16.11.2026 після Alt+Tab робочий стіл лишився
в 1400x1050.

## Власна частота оновлення (розгін монітора)

«Додаткові параметри дисплея» → «Власна частота оновлення»: вибрати частоту
вище за власні частоти монітора (від найвищої власної +1 до ×1,5), «Перевірити»,
далі, як для будь-якого режиму, питання «Зберегти ці параметри дисплея?» з 15 с.
Збережена частота стає звичайним режимом монітора: її бачать `EnumDisplaySettings`,
DXGI та ігри (CS2 тощо), і не лише на рідному розмірі, а на кожному розмірі, який
карта масштабує до рідних таймінгів (1280x960 @ 75 Гц на панелі 1920x1080).

Як це зроблено:

- Ключ монітора в `MonitorDataStore\<PnP id>`: `CustomRefresh` (binary, DWORD мГц
  кожна, до 4), `CustomRefreshTrial` (DWORD мГц, частота на перевірці),
  `CustomRefreshOff` (1 — не пропонувати). Панель пише, `dwmcore.c` стежить і
  передає в unix-частину (`dwm_set_options`: `custom*`).
- `kms.c`, `add_custom_modes`: таймінги найшвидшого власного режиму рідного розміру
  з вищою піксельною частотою, тип `DRM_MODE_TYPE_USERDEF`; той самий режим для всіх
  масштабованих розмірів. Бланк вибирає користувач (старші 4 біти значення частоти):
  0 — власний монітора, 1 — горизонтальний 80 px (CVT-RB v2), 2 — ще й вертикальний
  20 рядків (front porch і sync ті самі). Якщо драйвер відмовляє на власному бланку
  (не вистачає пропускної здатності лінка), береться 1 і запам'ятовується.
  У лог: `dwm: eDP-1 custom timings: ...`.
- Перевірено 16.11.2026 на MSI GP62M 7RDX (Innolux N156HGA-EAL, TN 60 Гц, 2250x1132):
  з власним бланком 65 Гц (165,6 МГц) чисто, від 67 Гц (170,6 МГц) артефакти, хоча i915
  приймав і 90 Гц. Межа — піксельна частота контролера матриці, не лінк: швидше лише з
  меншим бланком (2000x1132 — 73 Гц, 2000x1100 — 75 Гц за тих самих ~166 МГц).
- Масштабований режим (гра в 1280x960) на вбудованій панелі вищої частоти не дає:
  панель без власного скейлера, карта завжди шле їй 1920x1080 тих самих таймінгів.
- Вбудована панель (eDP/LVDS/DSI) на i915 завжди брала свій фіксований режим з EDID:
  `kernel/patches/0004` лишає таймінги режиму `USERDEF` рідного розміру
  (`i915.panel_user_timings=0` вимикає). Лінк перевіряється як для будь-якого режиму.

Захист, щоб екран не лишився темним:

| Що | Як |
|---|---|
| Питання в панелі | без «Зберегти зміни» за 15 с — назад (`confirm.c`) |
| Сторож у dwm | частота на перевірці без підтвердження за 20 с — назад, навіть коли панель зависла чи її закрили; одразу назад, якщо кадри не доходять 1 с або драйвер каже, що лінк упав (`link-status`) (`check_trial` у `compositor.c`) |
| Перезапуск | перевірка ніколи не переживає dwm.exe: на старті `CustomRefreshTrial` стирається |
| Старт із власною частотою | dwm ставить `CustomRefreshStarting` і скидає ключ на диск; через 2 хв знімає. Якщо наступний старт знаходить мітку (комп'ютер вимкнули на темному екрані), власні частоти вимикаються (`CustomRefreshOff=1`) |
| Win+Ctrl+Shift+B | будь-коли, наосліп: власні частоти вимикаються, монітори назад на свої частоти і налаштовуються заново (csrss → `ResetRefresh`/`Relight` у `Control\Power\ArcticDisplay`) |
| Вибір режиму без збереженої розкладки | власні частоти ніколи не беруться самі (`mode_for_attempt`) |

winewayland раніше лише додавав режими з `wl_output`; видалена частота лишалася в
`EnumDisplaySettings` до кінця процесу (Wine `0141`).

## Що ще лишилось у M2

- Кілька моніторів у QEMU перевіряються на virtio-gpu (`--monitors 2`); на
  залізі — два виходи RX 580.
- Монітори в desk.cpl нумеруються у зворотному порядку: `AddDisplayDevice`
  додає кожен пристрій у голову списку, тож `\\.\DISPLAY2` показується як «1».
  На саму розкладку це не впливає, але Windows нумерує їх за номером пристрою.
- «Додатково…» у desk.cpl показує лише загальну сторінку: `deskadp` і `deskmon`
  з ReactOS ще не збираються.
- Вимкнути окремий монітор («Приєднаний» у меню) поки не можна.
